# 独立开发者机会发现：意图与实现复核

日期：2026-09-12。范围：原始交接文档、全部现有迁移、API、保存逻辑、前端业务入口与本地运行数据。此文是修正建议，不表示下述模型已经实现。

## 结论

最初目标是“为 solo founder 持续发现需求、变现、获客已有部分证明，但仍有实际切入空间的 Web/App 机会”。目前交付的是网页采集、产品书签、原文检查与翻译基础层，尚不能发现或评估项目机会。基础层有可复用价值，但把它当作产品初版的主交付物是交付优先级偏差。

独立开发者是机会的实施主体；不强制要求所有参考产品本身都是一人公司。参考产品的创始人、团队规模、资金背景需要有来源和时间，未知不得推断。最终判断对象必须是较小的具体切入方案。

## 原始依据

工作区 docs/product-reference.md 与 Downloads/CODEX_HANDOFF_VENTURE_RADAR_V1.md 逐字一致。

- 第 1–4 节：面向 solo founder，winner-first，从已证实商业价值到痛点、获客、竞争缺口和 founder fit。
- 第 23、27、28 节：市场验证和竞争缺口分开；机会至少关联产品/市场及需求/痛点证据。
- 第 33、35 节：先验证最大未知；机会适合当前 founder 才有意义。
- 第 54 节：优化 Top-10 Opportunity Precision，不优化文档数、采集数和 AI 调用量。
- 第 58 节确实提出 200 产品/500 文档里程碑。此前实现进一步把它变成长期阻断业务闭环的门禁，且门禁在 API 中硬编码为 false。修正建议是将规模指标保留为后续基准验收，先用少量真实证据实现贯通闭环；单个机会仍然必须满足证据要求。这是对旧实施顺序的调整。

## 已确认的实现偏差

| 优先级 | 事实 | 影响 |
| --- | --- | --- |
| P0 | migrations 中没有 opportunities、pain_evidences、gap、distribution、validation、decision 对应业务表；前端机会入口是占位文案 | 无法表达“我应该验证哪个项目” |
| P0 | apps/api/src/app.ts 中 opportunities=0、qualityGate.passed=false、stage=FOUNDATION 固定返回 | 增加数据量不会开启业务能力 |
| P0 | winning_products 只有 domain/name、空目标用户/JTBD、monetization、proof_level 等；linkProduct 仅凭域名创建记录 | 保存了产品，并未分析其商业价值或可切入部分 |
| P0 | 缺少 customer segment → workflow → alternative → pain → gap → offer 的关系 | 多篇产品介绍无法转化为独立开发者项目 |
| P0 | founder_profiles 仅保存自由文本，不被机会筛选或评估使用 | “面向独立开发者”停留在设置页面 |
| P1 | sources 把 manual、winner、reddit 并列 | 人工导入方式、研究策略和内容平台混为一谈，无法可靠衡量来源独立性 |
| P1 | winning_products.domain 是唯一身份；一个平台域名下多个应用无法分别建模 | 不适合插件、应用商店项目及多产品公司 |
| P1 | revenue_signals 未包含指标语义（MRR/ARR/GMV/利润）、观测期、适用主体范围等；当前无写入业务链路 | 数额和月/年周期不足以表达商业证明，更无法据此排名 |
| P1 | 文档审核是整篇 accepted/rejected；没有具体声明的证据支持/反驳、适用人群或时效 | 文档质量通过可能被误当作每条商业结论都成立 |
| P1 | Signals 直接展示 raw_documents 的快照列表 | 重抓和解析变化占据注意力，原文数量易被误读为独立信号数量 |
| P1 | 中文要点存于 document_translations.result，不能关联机会中的具体论断 | 阅读助手没有变成机会推理层；精确摘录也不等于语义支持 |

运行时核对：3 个产品、5 个不同源文档、10 个快照、0 收入信号、0 人工接受记录、0 Reddit 内容。三个产品的目标用户和核心任务均为空，商业证明等级均为 0。此时不能诚实地输出经过验证的高质量机会。

## 建议的业务模型

围绕机会假设组织业务，而不是围绕来源网页组织产品体验。表名仅为建议，不做迁移或删库。

| 对象 | 必须回答的问题 | 核心内容 |
| --- | --- | --- |
| Product | 市场已有谁在提供什么？ | 稳定 ID、多平台标识、产品地址、目标人群、任务、收费、团队规模观察 |
| EvidenceClaim | 具体哪句话支持哪个事实？ | 声明类型、事实/推断/未知、原文快照与摘录位置、发布/观察时间、发布者、来源独立性、人工审核 |
| RevenueObservation | 有人实际付钱吗，规模如何？ | 产品/公司范围、指标类型、金额/区间/币种、观测期、披露/估计/验证分类、证据 |
| PainObservation | 谁在什么任务中付出什么成本？ | 人群、场景、任务、现用替代方案、问题、频率/损失/付费意愿（允许未知）、证据 |
| OpportunityHypothesis | 为谁做什么，为什么有切口？ | 付费者、任务、预期结果、参考产品、现有替代、缺口、最小方案、明确不做的范围、假设状态 |
| OpportunityEvidence | 每个判断凭什么？ | 机会、判断维度、声明、支持/反驳/背景角色、适用范围；多对多 |
| AcquisitionAssessment | 第一批用户怎么找到？ | 人群所在渠道、具体触达方式、渠道证据、转化假设、成本/限制、验证状态 |
| FeasibilityAssessment | 当前开发者能否持续交付？ | 关联 founder 配置版本、开发时间/依据、预算、维护支持、销售要求、平台与数据依赖、硬约束冲突 |
| ValidationPlan / Result | 先花最少的钱证伪什么？ | 最大未知、测试、人群/样本、预算/期限、成功/kill 条件、实际观察 |
| Decision | 最终为什么跟踪、验证或放弃？ | WATCH/VALIDATE/KILL、理由、证据版本、人工判断、投入和教训 |

关系：一个参考产品可以支撑多个不同切口；一个机会也可以参照多个产品。原文快照包含多个声明；同一篇页面重复抓取不增加独立需求数。同一声明可以支持或反驳不同机会，但必须指明具体判断维度。

产品域名是查重线索而非产品身份。证据链末端是原文快照，翻译只作展示。事实、推断和未知不能共用一个不透明的总分。

## 独立开发者筛选

先记录并应用硬约束：每周可投入时间、MVP 最大周期、预算、技能、能否做销售、可接受维护量、可获取数据及平台授权。用户未提供的项保持未知，不自行设定收入目标或预算。

再独立比较：付费需求证据、缺口可信度、可执行获客路径、实施/维护成本及风险。不因为大公司赚钱就给复制方案高分，也不因为产品是个人开发就认为值得做。未调查到的信息不打零分，不合成虚假的精确排名。

## 首个可用闭环与验收

1. 保留抓取、快照、任务、翻译模块；产品改为“参考产品”，补充多个身份标识。
2. 先允许人工录入及审核结构化声明/痛点，同时让模型建议提取，保留出处及不确定性。
3. 用 3–5 个参考产品及其真实需求材料贯通机会草稿、证据关联、适配评估和验证计划；不等 200/500 才实现业务。
4. 首页展示待核对/可研究的机会及缺少的证据；采集状态进入辅助页面。未满足最少证据的只显示在草稿区，不进入主机会榜。
5. 对每个候选能回答：为谁做什么、为何付钱、现有方案缺什么、如何找到用户、一个人能否交付、最大未知是什么、如何最便宜地验证。
6. 审核支持与反对证据；人给 Worthless/Interesting/Research-worthy/Strong 标签，之后才扩大来源与评估 Top-K 准确率。

Reddit 仍是原始规格中的 P0 来源。授权未完成应明确标记覆盖缺失；其他已授权材料可帮助实现和验证链路，但不能宣称已经满足 Reddit 验收。

## 迁移和范围

本次只做对照复核与目标模型建议，未修改数据库或业务逻辑。迁移应追加新对象并回填现有产品/原文关联，保留历史证据，不以删库重建解决设计问题。新的运营成本与 founder 偏好需要随后采集；不能从现有三家参考产品推断用户预算或技能。
